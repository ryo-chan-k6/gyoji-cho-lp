# GYOJI-CHO 事業戦略・プロダクト検証ロードマップ

最終更新：2026年8月16日

上位方針：[`business-roadmap.md`](business-roadmap.md)

本書の役割：Phase 0〜2を中心としたプロダクト検証戦略、MLP、Phase Gateの詳細

## 1. エグゼクティブサマリー

GYOJI-CHO（まいにち行事カレンダー 〜日本の行事帖〜）は、赤ちゃんの行事の日付を表示するだけのカレンダーアプリではない。

目指す最終形は、次の2つの表現で定義する。

- **日本の子育て行事OS**：子どもの情報を起点に、家庭ごとの行事時期を把握し、必要な情報と行動を適切なタイミングで届ける基盤
- **家族行事の意思決定と準備のプラットフォーム**：行事を知るところから、家族で決め、準備・体験・予約・購買を完了するところまで支援するサービス

主収益は、**準備・予約・購買に関する他社への送客／提携収益**とする。ただし、収益機能を先に作るのではなく、まずユーザーが行事を知り、準備し、体験する価値を実利用で検証する。

初期の需要検証ではWeb簡易MVPを作らない。少額広告で訴求だけを確認した後、**ちゃんと価値を感じられる最小iOS体験＝MLP（Minimum Lovable Product）**をValidation Releaseとして提供する。広告 → App Store → 実利用のファネルで、プロダクト需要と獲得チャネルを分けて評価する。

## 2. Missionと提供価値

### Mission

> **日本の文化を知って、体験し、心を豊かにする。**

Missionは長期的な存在理由であり、短期の広告コピーや機能訴求とは分けて扱う。需要検証の結果に応じてProduct Positioningは変更してよいが、Missionは安易に変更しない。

### Core Value

> **子どもの情報から、必要な行事を先回りして知らせ、準備まで支援する。**

### Primary User

> **第一子の妊娠後期から、子どもが満1歳の誕生日を迎えるまでの家庭で、赤ちゃんの行事について主に情報収集・判断・準備を担う保護者。**

集計上は妊娠後期と出生後0〜11か月を分け、1歳の誕生日を初期体験の終端イベントとして扱う。妊娠期流入は出生後Retentionが高くなる仮説を検証する独立コホートとし、出生後利用者と同じ主要KPI分母へ混在させない。詳細は [`D-001`](operations/decisions/d-001-primary-user.md) を正本とする。

このPrimary Userを中心に、次の課題を解く。

- どの行事を、いつ行うのか分からない
- 地域差や家族の意向があり、正解を決めにくい
- 予約、衣装、写真、食事、贈り物などの準備開始時期が分からない
- 情報が複数サイトや家族間の会話に分散する
- 気づいた時には選択肢が減り、準備が慌ただしくなる

### Extended Value

> **日本文化を知り、家族で体験する機会を提供する。**

必須ではない季節行事や風習について、読み物を届けるだけでなく、「今年はやってみる／今回はやらない」を選び、無理のない範囲で家族体験へ移れるようにする。

### 中核となる体験

> 子どもの情報を登録する<br>
> → 自分の家庭に合う行事が生成される<br>
> → 次の行事と意味が分かる<br>
> → 何を準備すべきか分かる<br>
> → 適切な時期に通知される<br>
> → 季節の文化体験にも出会える

機能数は少なくても、この体験は途中で切らない。

## 3. 対象ドメイン

| レイヤー | 内容 | 例 | 事業上の役割 |
|---|---|---|---|
| A. 家族固有の行事 | 子どもの生年月日等で時期が変わる | お七夜、お宮参り、お食い初め、初節句、1歳祝い、七五三 | コア価値、ユーザー獲得、将来収益 |
| B. 季節の文化体験 | 毎年訪れる日本の行事・風習 | 正月、七草、節分、ひな祭り、端午、七夕、お盆、十五夜、冬至、大晦日 | 継続利用、ブランド、利用の谷を埋める |
| C. 暦・文化背景 | 行事を理解する補助情報 | 二十四節気、七十二候、旧暦、六曜 | コンテンツ補助、データレイヤー |

初期プロダクトではAを獲得・課題解決の中心に置き、Bを少数だけ含めてExtended Valueとイベント起点Retentionを検証する。Cは主役にせず、行事体験を理解するために必要な範囲に限る。

### MLPの家族固有行事

`D-002`により、お七夜、お宮参り、お食い初め／百日祝い、ハーフバースデー、初節句、1歳祝いの6テーマを対象とする。生後1〜11か月の月齢マイルストーンも、共通テンプレートによる軽量な節目として含める。算出・準備・通知等の詳細は`P0-PROD-02`と`D-004`で固定する。

## 4. ポジショニングと競争認識

「誕生日等から行事日を算出し、カレンダー表示・通知する」機能には直接・隣接競合がある。したがって、**自動計算や通知だけを独自性としない**。

競争優位の仮説は次の組み合わせに置く。

- 家庭ごとの行事発生時期を先回りして把握できる
- 行事の説明ではなく、意思決定と準備完了までを一つの導線にできる
- 家族固有の行事と季節の文化体験を一つの体験として扱える
- 「やってみる／今回はやらない」を正常系として、親の負担を増やさない
- 行事直前ではなく、予約・購買に適した時期から提案できる
- 将来的に、体験と準備の実績から適切な外部サービスへ接続できる

競合の存在は課題の傍証にはなるが、GYOJI-CHOへの需要を証明するものではない。専用アプリをインストールし、子どもの情報を登録し、準備・通知・文化体験まで利用するかを実際のiOS体験で検証する。

## 5. 事業モデル

### 主収益：送客・提携収益

行事に必要な準備・予約・購買について、適切な事業者や商品へ送客し、成果に応じて収益化する。

| 領域 | 例 | 想定収益形態 |
|---|---|---|
| 写真 | 写真館、出張撮影 | 予約・問い合わせ成果報酬、将来の掲載料 |
| 衣装 | 祝い着、着物レンタル、子ども服 | 購入・レンタル成果報酬 |
| 会食 | レストラン、お祝い膳 | 予約成果報酬 |
| 贈答・用品 | 雛人形、五月人形、内祝い、記念品 | ECアフィリエイト、販売手数料 |
| 場所・体験 | 神社、祈祷、地域サービス | 送客、掲載、共同企画 |

### 収益化の順序

1. **Validation Releaseで準備意向を測る**：準備チェックリストと「詳しく見る」等の非提携導線からカテゴリ別関心を計測する
2. **既存ASP・アフィリエイト／予約サービス**：小さく成果発生を検証する
3. **個別事業者との成果報酬提携**：特定行事・地域で予約や問い合わせを検証する
4. **固定掲載＋成果報酬**：送客実績と高意向セグメントを基に直接提携を拡大する

実際の送客実装はPhase 4を基本とする。ただし、どの準備カテゴリに商業的需要があるかはPhase 1のMLPから計測する。

### 補助収益の扱い

- サブスクリプションは、低頻度利用との相性を検証できるまで主収益にしない
- ディスプレイ広告は体験を損ねやすいため、初期の主収益にしない
- 有料の家族機能、記録保存、コンシェルジュ等は、継続利用データを得た後の選択肢とする

### 守る原則

- 提携の有無で行事情報や推奨時期を歪めない
- 広告・提携・成果報酬であることを明示する
- クリック数より、ユーザーが納得して準備・体験を完了できることを優先する
- MissionとProduct Positioningを分け、広告反応だけでMissionを変更しない

## 6. 最新ロードマップ

| Phase | 名称 | 作るもの／行うこと | 検証目的 | この段階で判断しないこと |
|---|---|---|---|---|
| 0 | 事業仮説固定 | Core / Extended Value、対象行事、MLP機能、KPI、Analytics、Go / Pivot / Stop条件 | 開発前に仮説と撤退基準を固定する | 需要の有無 |
| 0.5 | 広告メッセージ検証 | 少額広告、既存LP、必要最小限の訴求別導線 | どの問題設定・表現に反応するか | 事業需要、プロダクト需要、PMF |
| 1 | iOS Validation Release | MLPとして成立する最小iOSアプリ | コア体験を欠けずに提供できるか | 広告経由での市場需要 |
| 2 | Product Validation | 広告 → App Store → MLP実利用、定量計測 | 実際に使った人が価値を感じ、戻り、準備行動を取るか | 正式v1の全機能、収益モデルの最終成立 |
| 2.5 | 定性検証 | 利用者・離脱者インタビュー | なぜ使った／使わなかったかを理解する | 数値だけによるGo判断 |
| 3 | 正式v1 | 検証を通過した機能の強化・拡張 | 継続的なプロダクト価値を作る | 未検証機能の一括追加 |
| 4 | Monetization Validation | ASP、アフィリエイト、事業者送客、提携 | 表示→クリック→送客→予約→成約、CACとLTV | 送客実績なしの大規模直接提携 |

### ロードマップの基本原則

- Web簡易MVPは実施しない
- LINE Waitlistの登録率をプロダクト需要の判定に使わない
- Phase 0.5の広告はメッセージテストであり、需要のGo / Stop判定には使わない
- Product ValidationとChannel Validationを別々に評価する
- MLPは「薄い機能一覧」ではなく「欠けていない最小体験」とする
- Phase 1着手前に対象行事、機能、計測イベント、Go / Pivot / Stop条件を固定する
- 収益機能は作り込まないが、準備カテゴリ別の意向はMLPから測る

## 7. iOS Validation Release：MLP定義

### 目的

> **ユーザーがGYOJI-CHOのコア体験に価値を感じるかを、本物のiOS体験で検証する。**

MLPは「最低限動くもの」ではなく、機能数を絞りながら、ユーザーが価値を感じる一連の体験を完結させたものとする。

### MLPの必須体験

```text
子どもの情報を登録
        ↓
自分専用の行事が生成される
        ↓
「次は○○」が分かる
        ↓
意味・やり方が分かる
        ↓
準備することが分かる
        ↓
適切なタイミングで通知される
        ↓
少数の季節文化にも出会える
```

### 必須機能候補

| 機能 | MLP | ねらい |
|---|---:|---|
| 子どもの生年月日・必要最小限の属性入力 | 必須 | パーソナライズ開始 |
| 家庭固有行事の自動生成 | 必須 | コア価値 |
| ホーム「次に来る行事」 | 必須 | 次の行動を即時提示 |
| 行事詳細・意味・一般的な目安 | 必須 | 日付計算以上の価値 |
| 準備チェックリスト | 必須 | 意思決定と準備支援 |
| ローカル通知 | 必須 | 先回り価値、イベント起点Retention |
| 季節の文化行事 | 必須・少数 | Extended Value、利用の谷の検証 |
| 準備カテゴリ別の関心計測 | 必須 | 将来の送客需要仮説 |
| 「やってみる／今回はやらない」 | 採否をPhase 0で決定 | 文化体験価値の検証 |

### MLPでは原則実装しないもの

- 独自ログイン・アカウント
- 独自バックエンドと家族情報のサーバー保存
- 独自家族アカウント共有
- 商品購入、予約、決済
- 提携店舗検索、レコメンド
- 地域別慣習の完全網羅
- 多数の行事・文化コンテンツ
- 高度な体験記録、SNS、コミュニティ

Appleカレンダー連携、簡易共有、体験記録は、MLPのコア体験または検証KPIに不可欠かをPhase 0で判断する。便利そうという理由だけでは追加しない。

### Local-first原則

- 生年月日、性別、行事情報は原則として端末内で保持・処理する
- 初期はアカウント登録を求めない
- サービス改善には、個人を直接特定しない行動イベントのみを収集する
- Analyticsへ生年月日等の個人情報を送らない
- 将来のバックアップ・共有も、可能な限りApple／iCloud等のユーザー管理領域を検討する

## 8. 検証設計

### Phase 0.5：広告メッセージ検証

少額広告で、例えば次の問題設定を比較する。

- A：赤ちゃんの行事課題
- B：調べる負担の解消
- C：家族で日本文化を体験する価値

見るものはCTR、CPC、LP到達後の最低限の行動など。ここでは、アプリ需要の有無や事業継続を判断しない。既存LPとLINEは、訴求理解や連絡希望を補助的に見るために利用できるが、Waitlist CVRを主要Gateにしない。

### Phase 2：Product Validation

| レイヤー | 主な指標 | 確認したいこと |
|---|---|---|
| Acquisition | 広告CTR、App Store到達率、Install CVR | アプリとして試したいか |
| Activation | 初回起動、生年月日入力完了、行事生成、最初の詳細閲覧 | パーソナライズ価値に到達するか |
| Value | 通知許可、準備チェックリスト利用、季節行事閲覧 | 今後も任せたいか、Extended Valueがあるか |
| Retention | D7 / D30、通知後再訪、行事詳細再閲覧 | 必要なタイミングで戻るか |
| Preparation Intent | 準備項目閲覧、カテゴリ別CTA、チェック完了 | 将来の送客需要があるか |

### Product ValidationとChannel Validation

- **Product Validation**：実際に使った人が、行事生成、準備、通知、文化体験に価値を感じるか
- **Channel Validation**：Meta等のチャネルから、経済合理的な水準で対象ユーザーを獲得できるか

広告CPAが高いことだけでプロダクト需要なしと判断しない。逆に、広告CTRが高いことだけでプロダクト需要ありとも判断しない。

### Event-triggered Retention

GYOJI-CHOは毎日使うサービスではない。D7 / D30だけでなく、次の行動連鎖を主要KPI候補とする。

```text
行事・季節文化の通知
        ↓
アプリ再訪
        ↓
行事詳細を閲覧
        ↓
準備チェックリスト／「やってみる」を利用
```

### Phase 2.5：定性検証

利用者と離脱者の双方に、以下を確認する。

- どの瞬間に価値を感じたか
- 何が不要・不足・不安だったか
- Web検索や他アプリの代わりになるか
- どの文化情報なら家族で体験したいか
- 準備で最も困ることは何か
- なぜ通知後に戻った／戻らなかったか

定量と定性を統合してGo / Pivot / Stopを判断する。

## 9. Phase Gate

### Phase 1開始前に固定するもの

- MLPの対象ユーザー
- 家族固有行事と季節文化の対象一覧
- MLP必須機能と明確な非対象
- Analyticsイベントと禁止データ
- Product / Channel Validationの指標
- Go / Pivot / Stopの数値・定性条件
- 開発工数・費用の上限
- App Store公開、プライバシー、安全性の要件

### Phase 2完了時の判断

- **Go**：コア体験と準備価値が支持され、正式v1へ進む
- **Pivot**：対象、訴求、行事範囲、機能、チャネルのいずれかを変更して再検証する
- **Stop**：コア体験が支持されず、合理的な修正仮説もない

数値基準は広告予算、必要母数、観測期間と一緒にPhase 0で決定する。結果を見た後に合格値を変更しない。

## 10. 重要なリスクと検証方法

| リスク | 早期に見るシグナル | 対応 |
|---|---|---|
| MLPを薄くしすぎる | 行事生成後に価値行動へ進まない | 機能数を減らしても、意味→準備→通知→季節文化の体験を切らない |
| Scope Creep | Phase 1前に便利機能が増え続ける | MLPスコープ、工数上限、変更承認条件を固定 |
| 広告成績を需要と誤認 | CTR／CPAとアプリ内行動が一致しない | Product / Channel Validationを分離 |
| 日次Retentionで誤判定 | D7 / D30は低いが通知後に利用される | Event-triggered Retentionを併用 |
| 準備価値はあるが収益につながらない | チェック利用はあるが商用カテゴリ関心がない | MLPからカテゴリ別準備意向を測る |
| 子どもの情報への不安 | オンボーディング離脱、入力拒否 | Local-first、アカウントなし、目的説明、最小取得 |
| 地域差・家庭差で信頼を失う | 日程修正、問い合わせ、低評価が増える | 一般的な目安と選択肢を示し、唯一の正解として扱わない |
| 季節文化が負担になる | 通知停止、「やらなければ」の反応 | 「今回はやらない」を正常系にし、頻度を抑える |
| コンテンツ運用が重い | 根拠確認と更新に過大な時間がかかる | 対象行事を絞り、出典・更新日・レビュー手順を持つ |

## 11. 意思決定のための北極星

最終的に最適化するのは、アプリの起動回数や広告クリック数だけではない。

事業の北極星候補は、**「対象行事について、期限内に1つ以上の準備または家族体験を実行した家庭数」**とする。

初期は直接観測できないため、次の代理指標を段階的に使う。

- Phase 0.5：訴求別反応
- Phase 1〜2：行事生成、準備項目利用、通知許可、季節文化閲覧、「やってみる」
- Phase 2：通知後再訪、準備完了
- Phase 3以降：体験完了、記録、家族共有
- Phase 4：納得した選択から生じる予約・購買
